# DeepDeep 架构与代码审阅总报告

审阅日期：2026-10-29（Asia/Shanghai）  
基准：`master@bdbaa07c17c7ac075b81804794e88252a00fbb61`  
范围：当前 `/home/whywood/project/DeepDeep`，SDK 以实际构建使用的 Maven Local `pi2kotlin 0.2.2` 为准。

## 总体结论

**项目有清楚的骨架和不少认真设计的局部，但会话运行的秩序尚未收敛。它已出现“多个功能各自正确、组合起来不可靠”的问题，不能仅凭功能可用和单测全绿评价为统一、成熟的架构。现在适合一次有边界的整合，不需要整体推倒重写。**

这里的关键区别是：文件夹已经分模块，不等于运行规则也被统一管理。DeepDeep 的界面、运行时、Linux、设计系统分层是清楚的；发送、重试、停止、提醒、目标续跑、插件重配却仍分散在 ViewModel、Host、AppGraph 和后台服务中。复现出的停止后仍重试、升级失败反而卸载旧插件、凭据内存/落盘不一致，正是后一种问题。

| 你关心的问题 | 本轮判断 | 依据 |
|---|---|---|
| 是否已经是“屎山” | 不能把整个项目这样定性；有正在形成的复杂度中心 | 核心入口有 1254/1036/726 行的协调文件，但也有纯 reducer、清晰插件接口、独立 shell、统一设计系统 |
| 是否靠胶水运行 | 必要适配层合理；业务时序的胶水明显过多 | SDK→App 事件适配和 Android→Linux 执行适配有必要；busy 观察、延时续跑、全量重配、UI 对账同时承担运行正确性则脆弱 |
| 模块化是否足够 | 构建模块边界较好，运行时边界不够 | `verifyModuleBoundaries` 通过；Host 缺少覆盖全部入口的单会话命令队列；临时工作目录未形成工坊权限边界 |
| 代码是否统一 | Kotlin/Compose、主题和状态风格较统一，错误/存储/取消语义不统一 | 多个独立 JSON Store；有的损坏抛异常，有的变空；同步凭据接口异步落盘；自动重试位于 UI 层 |
| 架构是否优美 | 有可保留的设计，但距离“统一整洁有序”还差核心约束 | 同一个会话由多种入口推动；停止和最终完成、提醒入队和已送达、临时目录和权限隔离尚未完全区分 |
| 是否应把整个 App 放进 Linux | 当前不建议 | Android 原生能力和系统生命周期仍必须由 Android 承担；Linux 应作为可替换执行后端 |

## 最需要先处理的事项

| 优先级 | 问题 | 证据等级 |
|---|---|---|
| P1 | 工坊 Agent 可用文件工具越过临时工作区；临时 cwd 不等于能力隔离 | 已用临时哨兵文件复现 |
| P1 | JSONL 损坏尾行使下一条新记录被拼接后丢失 | 使用实际 SDK 0.2.2 复现 |
| P1 | 自动重试倒计时期间按停止，仍会启动重试 | 实际 ChatViewModel + 仓库 fake runtime 复现 |
| P1 | 插件升级在下载等前置阶段失败，也会卸载原来可用的插件 | 实际 PluginManager + fake plugin 复现 |
| P1 | 上海时区全天日历日期被写到前一天 | 真实解析/转换函数联调复现 |
| P1 | 同会话多入口缺少统一串行化，运行 id/终态可互相覆盖 | 源码路径确认，尚未做 Host 并发实测 |
| P2 | 凭据异步写入乱序，内存显示新值、磁盘保留旧值 | 实际 SdkCredentialStore + 可控存储复现 |
| P2 | 时钟重新计算可直接禁用尚未送达的一次性提醒 | 实际 ScheduleStore 复现 |
| P2 | 无换行的命令输出可使流式缓冲无限增长 | 8 MiB 无换行输出复现 |
| P2 | 每条 Linux 命令都先遍历整个 rootfs | 源码确认并有合成目录耗时数据 |

P1 表示应在扩大使用范围前修复，P2 表示应在结构整理中处理；本报告没有用一个任意百分制来替代这些实际问题。完整条件、反例、修复方向和未验证边界见缺陷报告。

## 建议采取的总方向

保留 Kotlin/Compose、pi2kotlin Agent loop、Android 原生系统能力和可选 Linux 后端。围绕它们建立统一的会话命令队列、持久任务/提问状态、能力作用域、文件/输出契约和错误处理。先把“一个任务在任何入口进入、任何时刻停止、进程重启后都能解释清楚发生了什么”做扎实，再扩展自动化和工坊能力。
