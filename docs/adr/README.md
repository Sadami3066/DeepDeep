# 决策记录（ADR）

本目录记录「为什么这么设计」。它存在的唯一目的：**防止后续评审或 agent 把设计取舍当缺陷修掉**。所以每篇都写三件普通文档不写的东西——被否决的方案、接受了的代价、推翻条件。

读者首先是下一个改代码的人或 agent；实现细节不在这里（在 `docs/ARCHITECTURE.md`、`docs/DEVELOPMENT.md`），计划视图在 `docs/refactor/`。

## 状态约定

- **已采纳**：仓库现状与该决定一致；改相关文件前必须读完本篇并确认没有触发「推翻条件」。
- **已否决**：评估过、明确不做，但记录理由（防止同一个方案被反复提议）。
- **被取代**：新 ADR 取代旧 ADR。旧文正文不改，只在文首追加 `> 被 NNNN 取代`，索引里同步改状态。
- 已采纳 ADR 的正文**只增不改**：要改决定就新开一篇并在新旧两篇互相引用，不要原地重写历史。事实性补充（新增证据、路径变更）可以改，但要在文末「修订记录」留一行。

## 什么时候必须写 ADR

任一情况成立就必须写，而不是埋在 PR 描述或聊天记录里：

1. 决定会影响**用户数据**：签名、`applicationId`、备份/恢复、卸载清理、schema 迁移、损坏数据处理。
2. 决定是**放弃一个看起来更“标准”的方案**：单 Activity、不做审批、debug 签名、真机证据替代 UI 自动化、自研导航。
3. 涉及**外部契约、供应链、许可证或发布流程**：SDK 坐标、第三方组件捆绑、LICENSE/NOTICE、分发形态。
4. 评审/agent **反复建议、但当前明确不做**的项——把“不做”变成可引用决定，并在「被否决的方案」里给真实原因。
5. 改动**跨 >2 模块或触及热点文件**的结构性方案（`CONTRIBUTING.md` 硬规则已有“跨 >2 模块且无 ADR 直接退回”）。
6. 任何需要用「推翻条件」而不是「TODO」来管理的取舍。

不必写 ADR：纯实现细节、可逆的小重构、文案调整、测试补充——这些归 `docs/ARCHITECTURE.md`、`docs/DEVELOPMENT.md` 或代码本身。

## 每篇的固定结构

```
# NNNN 标题
- 状态：已采纳 / 已否决 / 被取代 · 日期 · 相关任务
## 背景      为什么必须现在决定（含现状证据）
## 决定      一句话可执行的决定 + 可回查的落地方式
## 被否决的方案   各一句 + 真实原因
## 后果      要接受的代价；哪些评审建议会因此被永久驳回
## 推翻条件   什么情况下这个决定不再成立，推翻时要做哪几件事
```

两条纪律：

- **决定必须能在仓库里找到对应证据**（文件、配置、行号、提交、命令输出）。写“应该”而不是“是”的句子不合格。
- **不写开发流水账**。过程、试错、临时结论一律不进 ADR；只留最终形态与理由。

## 与其他文档的分工

- `docs/ARCHITECTURE.md`：现在是什么（模块、数据所有权、启动顺序、不变量）。
- `docs/DEVELOPMENT.md` / `AGENTS.md`：怎么干活（命令、基线、边界）。
- `docs/refactor/`：接下来做什么（任务卡、阶段、已定决策的简表）。
- 本目录：**为什么**，以及“不要动它”的边界。当 `docs/refactor/README.md §5` 的简表与本目录冲突时，以本目录 + 仓库现状为准，并同步修正简表。
