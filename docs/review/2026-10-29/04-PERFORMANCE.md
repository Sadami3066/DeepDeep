## 环境与方法

主机：Linux x86_64，24 个逻辑 CPU，OpenJDK 21，Gradle 配置 2 workers；产品目标仍是 Android/Java 17 字节码。测量不是 JMH/AndroidX Benchmark，未锁 CPU 频率，未隔离整机负载，不能用于正式性能 SLA 或不同实现优劣的精确倍数比较。

每项数据均为最后一次完整观察运行：

- rootfs 状态：创建合成目录，预热 2 次，9 次采样，报告中位数/最大值。
- 会话列表：每文件约 22KB 的 20 条合成 message，加 header；预热 2 次，7 次采样。约 22.08MB/1000 文件；SDK 会读取并解析全量内容。
- Markdown：标题、段落、列表、表格、代码块组合，预热 10 次，21 次采样；p95 为排序后的第 20 个样本，样本很少。
- reducer：预建历史，20 次预热 delta，每个样本连续归约 100 个 delta，21 次采样。包含状态复制/字符串增长及 JVM 分配噪声，不含 Compose 绘制。

原始输出：[audit-tests.log](evidence/audit-tests.log)；用例源码：[harness](harness/)。多次运行数字会波动，不能选其中最好的一组当产品承诺。

## 已完成的本机数据

### Linux 状态检查

| rootfs 文件数 | 中位数 ms | 最大值 ms |
|---:|---:|---:|
| 100 | 0.935 | 2.468 |
| 1,000 | 3.913 | 6.859 |
| 10,000 | 27.208 | 44.264 |

最值得优先消除的固定开销。每次 execute 都进入 `currentState → readState → Files.walk`，规模与已安装工具文件数相关。应将执行前“是否可运行”的 O(1) 检查与设置页“占了多少空间”的异步统计分离。

### SDK 会话列表扫描

| 会话文件数 | 总字节约 | 中位数 ms | 最大值 ms |
|---:|---:|---:|---:|
| 10 | 220,781 | 3.643 | 5.908 |
| 100 | 2,207,892 | 14.419 | 21.303 |
| 1,000 | 22,079,893 | 63.906 | 70.383 |

这些数值只说明小规模合成日志在热缓存下的结果。真实 Agent 长日志可能远大于每会话 22KB；`list` 解析完整 JSONL，本质成本按总字节增加。App 刷新未归档/归档还会重复扫描；某些提醒/事件刷新也会触发存储读取。

建议增量会话索引，保存 sessionId/cwd/title/createdAt/lastActivityAt/file stamp，列表不读取全部正文；正文搜索单独做可取消的索引或按需扫描。索引是投影，JSONL 仍是消息权威。

### Markdown 解析

| 输入字符数 | 中位数 ms | 小样本 p95 ms |
|---:|---:|---:|
| 1,240 | 0.228 | 0.321 |
| 12,400 | 1.745 | 1.954 |
| 124,000 | 7.271 | 10.453 |

静态上 `ChatMarkdown` 在 Compose 中 `remember(text)` 解析全文；稳定文本有缓存，但流式 text 每批变化就会重新解析。主机 124K 字符的 7.27ms 不等于手机同样耗时；它已经提示主线程重复全文解析的成本不能忽略。

建议已结束块冻结、仅解析最后未闭合块；或把长文本解析放可取消的后台任务，并校验 text revision 再提交。不要因异步解析让旧文本覆盖新文本。

### 聊天 reducer

| 既有消息数 | 每样本 delta 数 | 中位数 ms | 小样本 p95 ms |
|---:|---:|---:|---:|
| 100 | 100 | 0.308 | 0.619 |
| 1,000 | 100 | 1.058 | 1.584 |
| 10,000 | 100 | 9.531 | 11.716 |

这是 100 次归约合计，不是单帧耗时。不可变列表/步骤复制和逐段字符串拼接在大历史下增加分配；当前 16ms delta 合批已经减轻事件频率。先测清列表/解析/布局哪一项占主导，再考虑持久集合、rope 或流式 buffer，不能凭这些数据断言必须替换 Compose。

## 静态热点与优化收益判断

| 路径 | 已有保护 | 剩余问题 | 优先级 |
|---|---|---|---|
| Linux 命令前置检查 | marker/版本、安装 SHA 校验 | 逐命令遍历全 rootfs | 高：移出关键路径，行为不变 |
| 无换行 stdout | 最终 output 64KiB、下游 ring 256KiB | 上游 pendingLine 无界 | 高：先防失控，再谈速度 |
| SDK read 大文件 | 输出行数/字节裁剪 | 先整文件读入再裁剪 | 高：流式读取输入 |
| 会话目录 | IO dispatcher、UI 缓存 | 列表扫描全文/重复扫描、排序字段混用 | 中高：增量索引 |
| 聊天流 | 16ms 合批、runId 丢弃旧事件 | 全文 Markdown 重解析、列表复制 | 中：基于 trace 决定增量实现 |
| 已打开 session | 多会话不互相关闭，切换体验好 | handles/cache/MCP 连接无明确空闲预算 | 中：静态风险，不给内存数字 |
| job 输出 | 256KiB 实时/16KiB 结束缓冲 | 每次输出 publish 所有任务快照；已结束记录保留 | 中：限制发布频率、增量状态、保留期限 |
| 工坊 Agent | 180s/最大 64 turns | 每次复制技能、新建 session；并发调用无全局限制 | 中：显式能力/并发配额，缓存只读技能 |
| 插件重配 | 等全部空闲 | 重建所有 session/MCP，等待不是锁 | 高：安全点局部重配，先保证正确性 |
| 图片/动画 | 8MB 缩略图 LruCache、解析 remember、graphicsLayer | 仍需真机 trace 才能判断实际帧表现 | 保留已有优化，本轮不扩大结论 |

## 构建和交付体积

当前 debug APK 约 48MB，包含 SDK、Compose、字体和约 4.03MB 的 Alpine rootfs 压缩资产。没有 release/profileable 性能基线，不能拿 debug 包代表用户最终启动、体积或帧表现。没有给出 PRoot 相比原生的固定损耗百分比，因为本轮没有同设备同任务 A/B。

正式性能基线可在之后以 release/profileable + Macrobenchmark 的 StartupTimingMetric/FrameTimingMetric 和固定输入重建；Android 官方推荐用 Macrobenchmark 测启动、滚动和复杂 UI 交互，并保留 JSON/trace。此处是后续方法建议，不代表本轮已运行。[官方说明](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview)
