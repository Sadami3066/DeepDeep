总体结论

项目有清楚的骨架和不少认真设计的局部，但会话运行的秩序尚未收敛。它已出现“多个功能各自正确、组合起来不可靠”的问题，不能仅凭功能可用和单测全绿评价为统一、成熟的架构。现在适合一次有边界的整合，不需要整体推倒重写。

这里的关键区别是：文件夹已经分模块，不等于运行规则也被统一管理。DeepDeep 的界面、运行时、Linux、设计系统分层是清楚的；发送、重试、停止、提醒、目标续跑、插件重配却仍分散在 ViewModel、Host、AppGraph 和后台服务中。复现出的停止后仍重试、升级失败反而卸载旧插件、凭据内存/落盘不一致，正是后一种问题。

3. 发出一条消息后如何运行

3.1 输入归一化

ChatViewModel.send() 检查 ready/historyLoaded、当前会话、sending/切换状态，裁剪空白并解析命令。人用 /compact、/goal 由应用命令处理；技能引用经 SkillCatalog 展开为提示词。附件通过 <attachments> 文本块描述实际工作区文件，引用内容由 buildPrompt() 拼接。

发送的 UI 先乐观添加用户消息和一个运行中的助手占位，清空输入/附件/引用，设置 sending。随后等待当前会话的打开任务，调用 runtime.send(sessionId,prompt)。这次用户主动发送的运行协程属于 ViewModel；后台提醒/目标/任务唤醒由 AppGraph 的后台 scope 推动。生命周期归属并不完全统一。

3.2 Host 的一次运行

Host 找到 Handle，beginRun() 生成 UUID runId，写 turnSource、startedAt、busy、stopRequested、terminalEmitted，并发布 busySessionIds 和 activeRuns。新会话尚无标题时先追加标题，以便抽屉立即看到会话。

然后发布 RunStarted、Thinking，调用 session.prompt(text)。模型回答需要工具时，SDK 执行工具，写入结果，再让模型继续。这整个内部循环由 SDK 负责；DeepDeep 没有在 Host 里重写一个模型/工具 while-loop。

5. 提示词、模型与凭据

PiSessionEngine.createSession() 的工作顺序是：确保全局 SYSTEM.md → 解析 fallback 配置 → 如果打开文件则读取其模型 → 构建工具和 SessionBinding → 生成初始 section → createAgentSession() → 绑定 session。

工具定义通过 SDK/provider 的真实 tools 字段发出；文字提示词中的规则只说明怎么用。SYSTEM.md 的自定义前言、工具 guidelines、动态 environment、长期 instruction、插件 prompt、技能和工作区文档共同影响模型。environment 按天更新日期，读取 session 当前模型和 cwd，避免每一帧/每一秒改变 system prompt。

ProviderCatalog 从 SDK 目录映射 App 模型/思考等级。ProviderOAuthService 调 SDK OAuth flow，Android loopback 工厂承接浏览器回调并跳回 deepdeep://oauth/...。安装身份通过 install-id 保持稳定。MCP OAuth 走独立 token store。

凭据的关键结构是“异步磁盘 + 同步 SDK”：Key/OAuth 原始 JSON 加密落 DataStore，SdkCredentialStore 缓存给 SDK 同步读，同时发布 authKinds/revision 给界面。缓存立即变化、磁盘写入另起协程，所以排序/失败/进程死亡窗口需要专门治理，不能仅依赖 DataStore 本身单次写事务。

7. Linux 如何工作以及共享了什么

LinuxRootfsInstaller 校验捆绑 Alpine 3.24.2 aarch64 rootfs 的 SHA256，解包到临时目录，写 marker，再发布到 files/linux/rootfs。PRoot 二进制来自 arm64-v8a 的 native library 目录。当前 Linux 仅支持 arm64-v8a。

每条 bash 启动一次 PRoot，绑定 /dev /proc /sys、当前宿主 cwd→/workspace，以及 skills、skill-repo、gui、micloud 等目录；共享存储开关允许 /sdcard 映射。环境变量在进程启动时显式设置，命令由 guest /bin/sh -c 执行。

flowchart LR
  Tool[bash / job / CLI 插件] --> Adapter[LinuxShellExecutor / LinuxJobRunner]
  Adapter --> Env[LinuxEnvironment 按 cwd 缓存]
  Env --> State[检查 marker 和 rootfs 大小]
  Env --> Proc[PRootExecutor / worker + watchdog]
  Proc --> Bind[当前 cwd 绑定到 /workspace]
  Proc --> Shared[共享 rootfs / root / usr / CLI 凭据]
  Proc --> IO[合并 stdout + stderr]
  IO --> Cap[前台最多保存 64 KiB]
  IO --> Line[后台按行推送]
  Line --> Ring[JobRegistry 环形缓冲 / 游标]

不同会话的 /workspace 不同，但 rootfs、/root、CLI 登录态和全局技能目录是共享的。用户在会话 A 安装包，会影响 B。这不是每会话一个容器。临时工坊 Agent 如果取得 shell，也会复用同一个执行环境结构。

前台 bash 默认 60 秒、允许 1..600 秒；job 最多 24 小时。超时/取消尝试杀死进程树。前台保存前 64KiB 输出，没有通用溢出文件回读；后台输出实时环形缓冲 256KiB、结束裁成 16KiB，单个任务的增量游标由 Record 保存。

11. 停止、失败和恢复

停止当前路径：UI→Host.stop()，立即发 STOPPED 终态，再 session.abort() 发取消信号。SDK 0.2.2 还有 waitForIdle() 和 Settled；当前 Host 停止语义没有统一等到这些信号后才完成状态转换。随后 runTurn 的 finally 清 busy/activeRuns，UI 必要时从 history 重建。

失败路径：Host 检查末尾 stopReason 并区分 Error/Aborted，SDK SessionError/RetryExhausted 也会走终态。ViewModel 再根据本地化错误类别决定最多 5 次、间隔 2 秒的自动重试；手动重试调用 SDK retryLastAssistant()，用 context edit 移除末尾失败 assistant 后继续，避免重复用户消息。

恢复路径：JSONL 重建历史、模型与上下文；DataStore/JSON 恢复工作区/配置/目标/提醒；busy/activeRuns 与内存缓存不跨进程保留；job 和未答问题没有完整执行恢复。进程死亡不会因为运行环境是 Linux 就消失：PRoot 命令仍属于 Android 应用生命周期下的进程资源。Android 官方进程生命周期说明进程存活由系统综合决定。

质量与缺陷

代码质量与缺陷

总体结构判断

代码已经有四个值得保留的基础：单向构建模块、独立于具体 UI 的 AgentRuntime 接口、可测试的 ConversationReducer、统一设计与官方插件接口。SDK 负责模型循环，Host 负责 App 会话投影，Linux 实现 ShellExecutor，这种分工成立。不能因为存在适配代码就称为“胶水”，也不能只因为大文件就断言为坏代码。

真正的问题是多个子系统对同一个事实分别做决定：

事实 当前散落位置 已造成或可能造成的后果
会话是否可以开始运行 ViewModel.sending、Host.busy、SDK.activeOperation、后台回调 UI 的防重复不保护后台入口，runId/终态可覆盖
停止是否完成 ViewModel.stop、Host.stopRequested/STOPPED、SDK.abort、PRoot kill 停止信号、UI 终态、进程真正退出被混合
是否应该重试 SDK retry loop、ViewModel 自动重试 用户停止没有取消 UI 侧倒计时；两层重试的总预算不清楚
能力是否改变 PluginManager、MiCloud 开关、AppGraph wait-empty、Host.reconfigure 等待空闲与真正重配不是一个原子操作；会话整体重建
数据是否已可靠保存 内存 cache、异步写、各 Store 的临时文件/错误策略 UI 显示成功和磁盘提交成功并不总一致
工坊是否隔离 独立 origin、临时 cwd、工具名字过滤、共享 Linux 网页 origin 隔离被误当成 Agent 能力隔离

这些是结构性复杂度，靠再加几个判断容易继续变复杂。最优先的重构目标应是把这些事实各自收回一个明确的所有者。

统一性具体评价

  • 视觉较统一：主题、Dd 组件、motion、图标和常见菜单被集中管理；缩略图 LruCache、工具卡解析 remember 和 graphicsLayer 动画有明确优化意图。
  • 类型大体统一：RuntimeEvent/AssistantMessage/ToolTrace、sealed interface、Flow 与不可变状态是通用风格；但 SDK 类型通过 runtime/shell 的 api 依赖向 app 暴露，工具 schema 与 App 领域模型相连较深。
  • 存储策略不统一：目标/提醒损坏会抛异常，插件记录损坏返回空记录加错误，会话目录删除吞异常，SDK JSONL 追加没有尾部修复。并非所有数据都需要相同存储格式，但成功/损坏/恢复语义需要一致。
  • 并发策略不统一：Mutex、synchronized、AtomicReference、StateFlow、全局 busy、延时和 UI 再对账并存。机制多不是问题，缺少明确的每会话所有权和原子状态迁移才是问题。
  • 错误与取消不统一：部分模块显式重抛 CancellationException，部分 runCatching 或网络阻塞调用没有贯穿取消；工具文案里存在中文/双语硬编码，ChatUiStrings 又另行分类。
  • 文档存在漂移：ARCHITECTURE 中“模型切换同步到所有会话”的旧描述与当前按 sessionId 切换实现不一致；STATUS 是历史证据，本轮 lint warning 数也不同。文档不能替代代码或本轮实测。

证据等级与严重性

“复现”指真实项目类/当前 SDK 在隔离测试中表现出问题；Android 和第三方服务依赖可以由可控替身提供。“静态确认”指明确存在相关代码路径，但未测出设备端后果。“风险”不等于已经观察到线上故障。P1/P2 是修复顺序，不是声称每个问题都能远程利用。

审阅用例在本目录 harness 中，通过额外 Gradle init 文件接入，未改原测试目录。测试断言记录当前有问题的行为；修复后应改成断言正确行为。

B01 [P1，已复现] 工坊 Agent 可越过临时工作区

触发：网页经 app.agent.run() 使用默认工具，Agent 调 read/write 或取得 bash。
行为：workshopAgentToolVisible() 只排除 arrange_/mi_cloud_/gui_ 前缀；原生 read/write/edit 等仍在。SDK resolveToolPath 允许绝对路径和 ..，文件系统是 FileSystem.SYSTEM，没有 scoped wrapper。临时 cwd 仅改变默认相对目录。

隔离用例在临时目录创建 isolated-workspace 和兄弟哨兵文件，通过实际 SDK read 工具读取 ../outside.txt 成功。没有读取用户真实文件。由源码可推导同 UID 可访问文件可能暴露；本轮没有测试 Android Keystore 解密或跨 UID 访问，不能把该结果扩大为读取所有手机数据。

来源：工坊过滤、工具与 FileSystem.SYSTEM、当前 SDK 路径解析。

修复契约：给工坊显式允许的工具和数据范围；文件工具验证 canonical 路径及 symlink；shell 必须单独授权或交给真正有隔离保证的后端。单纯黑名单或 system prompt 不能形成这个边界。MCP 在工坊中确实关闭，此点不应误报。

B02 [P1，已复现] 崩溃尾行吞掉下次写入

触发：JSONL 末尾出现半条记录，重新打开后追加新记录。
行为：读取器跳过无效 JSON，写入器直接 appendingSink，不在追加前截断/隔离尾部或补齐记录边界。新记录与坏尾拼为一行，再打开后整行被跳过。

用例先写有效 header、名称 before 和损坏尾行；重开追加 after-crash；再次重开名称仍是 before。用的是当前构建对应的 SDK 0.2.2，而非旧版本记忆。完整但缺换行的尾行也存在追加边界风险；本轮主要复现的是半条尾行。

来源：实际持久化代码、复现用例。

修复契约：SDK 层启动时扫描并修复最后有效记录边界，坏尾另存，追加必须保证 LF；写入崩溃点、重开追加、再重开可见性必须一起验收。这项修复应进入 pi2kotlin，再发布并在 App 集成验证。

B03 [P1，已复现] 停止未取消自动重试倒计时

触发：自动重试已启用，网络失败后进入 2 秒等待，此时点停止。
行为：stop() 只调用 runtime.stop；这时 runtime 可能已经没有 active run，停止无事可做。autoRetryJobs[sessionId] 未取消，延时结束仍 beginRetry()。

实际 ChatViewModel 与仓库 fake runtime 联调：发 RunFailed(network error) → stop → 前进 2.5 秒，runtime.retryLastTurn 调用计数为 1。

来源：自动重试、停止入口、复现。

修复契约：Stop 取消该会话所有待启动重试/目标续跑/后台 run 请求，递增执行 epoch；旧 epoch 的延时任务不能复活。短期可先 clearAutoRetry，但最终要收回统一运行控制器。

B04 [P1，已复现] 升级失败破坏旧插件

触发：已经安装 1.0 的插件更新到 2.0，下载/安装阶段失败。
行为：installInternal() 的异常分支无条件 plugin.uninstall()，即使新包尚未替换旧包。旧安装记录保留，技能还可能被删除。

用实际 PluginManager 和 fake 插件复现：升级前 installed=true；install 在替换前抛错；升级后 installed=false，但持久记录仍是 1.0，UI 的 snapshot.installed 仍为 true。对飞书这种 uninstall 会删除 CLI 配置/数据目录的实现，潜在后果包含重新授权；本轮没有用真实账号执行此场景。

来源：升级与异常处理、飞书卸载内容、复现。

修复契约：下载校验→暂存安装→健康检查→切换版本→提交记录；失败回滚旧版本，不能用“卸载整个插件”清理一次失败升级。首次安装清理和已有安装升级必须分开。

B05 [P1，已复现] 全天日历事件日期偏移

触发：Asia/Shanghai 下输入 2026-10-30、allDay=true。
行为：parseCalendarMillis 先按上海零点转成 2026-10-29T16:00Z，resolveEventRange 再向 UTC 零点取整，得到 10 月 29 日；返回显示也为 10 月 29 日。

现有测试分别验证了本地日期解析与 UTC 取整，却没有组合二者。真实函数联调复现 requested=2026-10-30、actual=2026-10-29。Android Calendar 的全天事件应使用 UTC 对应日期边界；应从 LocalDate 直接编码该日期，而不是把一个当地时间 Instant 粗暴向下取整。Calendar 官方契约

来源：日期解析、UTC 取整、复现。

修复契约：全天事件保留 LocalDate/日期范围；普通事件保留 Instant+ZoneId。分别覆盖正/负时区、跨日和夏令时，验证实际 Provider 保存日期。

B06 [P2，已复现] 凭据写入未按 Provider 串行

触发：短时间内保存新凭据、OAuth 刷新/切换认证方式，旧写入恰好较慢。
行为：缓存同步更新，磁盘各自 scope.launch(ioDispatcher)；先调用的协程不保证先提交。pendingWrites 是 Set，无法表示同一 provider 多个写入数量/版本。

在旧 saveRecord 被可控挂起的替身中，先写 old、再写 new、释放 old：内存 new，磁盘 old。加密/DataStore 的单次写事务不能替代上层“最后一次用户意图获胜”的排序。该用例没有测真实手机磁盘出现频率。

来源：异步写、复现。

修复契约：按 Provider 的串行队列/修订号、可 await 的提交、失败状态回传、刷新与登出互斥；重启后最新值保持，禁止旧刷新 token 在登出后重新落盘。

B07 [P2，已复现] 时钟重算会跳过未投递提醒

触发：一次性提醒原定 09:01，尚未投递，系统时钟调整后当前时间为 09:02，触发 recomputeTargets。
行为：nextRun(now) 返回 null，被直接 enabled=false、nextRunAt=null；lastDeliveredAt 仍为空。该次提醒失去补投机会。

另一个静态限制：ScheduleStore/Service 默认创建 Clock.systemDefaultZone() 并长期保留，该 Clock 的 zone 是创建时固定的；仅调用同一个 Store 的重算不等于重新读取系统新时区。本轮未做手机改时区实验。

来源：重算、广播、复现。

修复契约：把“已错过尚未投递”与“无下一次”分开；先处理 overdue/outbox，再按当前 zone 重算未来触发。

B08 [P2，已复现] 输出有上限，行缓冲却没有

触发：后台命令输出很长、一直没有换行。
行为：result.output 只保存 64KiB，但 pendingLine 对每个字节持续累积，直到换行/EOF 才回调；下游 256KiB ring 无法限制它上游的内存。

8MiB 无换行输出：最终 output=65,536 字节且 truncated=true，但单次 callback_chunk=8,388,608 字符。更大输出的内存增长由源码直接可见；本轮没有进行 OOM 或手机内存测试。

来源：pendingLine、复现。

修复契约：按有限大小字节块发布、增量 UTF-8 解码、独立输出文件和游标回读；行仅作为展示形式。分别限制读取缓冲、事件队列、持久输出和模型上下文。

B09 [P2，静态确认 + 性能观察] 每条 shell 命令扫描全部 rootfs

LinuxEnvironment.execute/executeStreaming 调 installer.currentState()，进入 readState→directorySize→Files.walk(rootfs)。已安装标记校验和展示磁盘占用被绑在一起。LinuxEnvironment 的安装状态初始化也会走同样路径。

合成 100/1,000/10,000 文件目录，本机状态检查中位数约 0.93/3.91/27.21ms；这是 JVM + 热文件缓存结果，不能当手机耗时。安装 Node/CLI 后大量文件会提高每条命令的固定成本。

来源：命令前检查、目录扫描。

修复契约：执行前只做 O(1) marker/状态检查；大小统计异步按需/缓存；安装/重置后失效。

R01 [P1，静态高风险] 多入口可覆盖同一个会话的运行状态

send() 在拿出 handle 后不检查 busy，不把 beginRun 放在单会话锁里。deliverReminder/deliverBackgroundTurn 的 busy 检查与 beginRun 也不是原子操作。后台 scope 是 IO 多线程，不能假设只会从 UI 单线程进入。

可能交错：A、B 都看到空闲 → A beginRun/runId=A 启动 prompt → B beginRun 把 runId 改成 B → B 的 SDK prompt 报 busy → B finally 无条件 busy=false，并可能清 runId；A 仍执行，事件归属/终态已经被污染。SDK 自己拒绝 busy，并不能回滚 Host 已经改坏的状态。

来源：send、后台入口、beginRun。

没有做 Host + 真正慢模型流的竞态复现；按静态高风险处理。修复需用每会话 actor/队列覆盖 send/retry/stop/followUp/compact/reconfigure/close，并给所有命令 run epoch，而非再加一个 UI 防重复按钮。

R02 [P1/P2，静态高风险] 插件重配可能关闭刚启动的会话

AppGraph 多处 busySessionIds.first { it.isEmpty() } 之后调用 reconfigure。等待结束和重配之间可以开始新 run；Host.reconfigure 自己没有原子地检查“无运行 + 阻止新运行”，而是全部 detach 再 attach。

来源：AppGraph 能力变更回调、全量重配。

修复：每会话在安全点更新工具快照/版本；或由同一个会话队列提交 reconfigure。避免用观察到空闲作为执行锁。未做设备复现。

R03 [P2，静态确认] 目标续跑预订后没有再次检查目标版本

Host 在成功时先 driver.nextRound()，再延时 400ms。真正投递时只检查 !handle.busy。如果这段时间用户 pause/clear/edit goal，旧 GoalRound 仍可能发起；如果会话恰好忙，轮次已递增，但续跑请求被直接跳过。

来源：续跑延时。修复应携带 goalId/revision 和可取消的待运行请求，在队列内复核；轮次计数在实际开始时提交。

R04 [P2，静态确认] 附件大小检查可被未知长度绕过

FileAttachmentStore.import() 只比较元数据 size>25MiB；size=-1 或上游填错时仍 input.copyTo(output) 到 EOF，没有边复制边限额。与 PluginDownloader 的 written 上限实现不一致。可能占用大量磁盘/IO，尚未做 Android ContentProvider 复现。

来源：导入大小与 copyTo。修复：流式计数并提前终止/清理；导入完成时复核接收会话，防止导入过程中切换会话后把附件加入另一个会话状态。

R05 [P2，静态确认] SDK read 的输出限制不限制读取内存

SDK read 工具先 fs.read { readByteArray() } 读整文件、解码、split，再按 offset/limit 裁剪。读大型日志时，即使只要求几行，也会加载整文件。这是 SDK 层的问题，不应归罪于 Compose。

来源：实际 ReadTool 0.2.2。建议 text 流式逐行/分块读取，图片先查大小/格式并采样；用真实大文件验收峰值分配需另行授权测试。

R06 [P2，静态确认] 会话最近活动排序可能退化为创建时间排序

SDK SessionManager.list 内部按 mtime 排序，但 SessionInfo.timestamp 装的是 header.timestamp。SessionCatalog 又转成 updatedAt 后重新排序；header 通常是创建时间。因此继续较老会话并不保证按本轮活动时间排到最新。

来源：SDK loadSessionInfo、目录 updatedAt 映射。建议把 createdAt 和 lastActivityAt 分成两个字段，建立持久索引；本轮未做真实抽屉 UI 复现。

R07 [P2，静态风险] 长期打开的会话与任务缺少资源淘汰策略

Host.handles、AppGraph.shellEnvironments、ChatViewModel.conversationCache，以及未移除的 JobRegistry settled records 会随着使用积累。打开多个带 MCP 的会话，还会保留各自连接/SDK 状态。不能从此静态事实断言已经内存泄漏或给出手机内存数字；目前可确认的是缺少明确的空闲关闭/缓存预算/保留期限。

建议：运行会话保持活跃，空闲 SDK handle 按 LRU/数量上限关闭；UI 只缓存有限消息摘要；历史/任务详情从持久记录按需加载。按用户要求，本轮不做内存实测。

R08 [P2，静态风险] 持久性与成功语义不够完整

  • Reminder 交给 Host/排队就 markDelivered；进程在实际 prompt 前死亡时，投递状态与执行事实之间存在窗口。
  • QuestionCenter 与 job 都只有内存权威，进程死亡后无法向用户说明等待问题/未知工具结果的完整状态。
  • SDK JSONL 是会话权威，但目标/任务/问题不应靠聊天文本前缀反向解析成自己的唯一状态。
  • 同 cwd 的多个 session 各有 FileMutationQueue，原生写/edit 不跨会话串行；bash/CLI 又可绕过该队列。当前没有跨入口的文件观察版本/提交冲突契约。

上述是可靠性设计缺口，未声称每一种窗口均已复现。应建立任务/outbox、幂等键、unknown-outcome 与恢复状态，具体见架构建议。

测试质量为什么不足以抵消这些问题

804 个现有测试通过是有价值的回归证据，但它们主要验证纯规则和替身边界。没有覆盖本轮发现的跨函数时区转换、停止与延迟重试、失败升级保留旧安装、损坏文件追加等组合场景。当前缺少直接驱动真实 Host 多入口的系统性生命周期测试，Android instrumentation 只有一个日历 CRUD 测试文件。

没有执行覆盖率工具，79 个单测 Kotlin 文件也不等于 79 个产品模块都有相同比例覆盖。建议把测试投资转向执行不变量/故障注入，而不是单纯增加测试数量。完整验收矩阵见 06。

整合与产品建议

产品方向与架构整合建议

1. 建议选择的路线

保留 Android 原生宿主和 pi2kotlin，把 Linux 定位为可选、可替换的执行后端；先统一任务和会话运行规则，再增加能力。 当前缺陷没有证据表明是 Kotlin/Compose 或 SDK 适配这种路线本身造成，换到 Linux 不会自动修复停止、持久化、升级和权限作用域问题。

Android 应用本来运行在 Linux 内核之上；这里真正要选择的是“Agent 控制逻辑运行在 Android/Kotlin 进程，还是运行在 PRoot/Termux 中的独立服务”。PRoot 是基于 ptrace 的用户态路径/进程环境转换，不提供独立 guest kernel；将控制逻辑放进去仍然受宿主资源和 Android 生命周期约束。PRoot 官方说明

可选方案比较

方案 好处 新成本与约束 对当前产品的判断

这里没有声称某方案快多少。任何迁移都应对固定任务、同模型/预算、相同取消/恢复条件做对比；当前证据更支持整理控制平面，而非更换执行语言。

2. 产品应该围绕“任务”收敛

当前产品已有聊天、目标、提醒、job、插件、MCP、工坊、语音等入口，但用户最终关心的是“这件事现在进行到哪里、需要我做什么、做完交付了什么、失败能否继续”。建议形成如下产品关系：

flowchart LR
  Input[聊天 / 语音 / 分享 / 提醒 / 工坊] --> Task[一个任务及其状态]
  Task --> Session[模型会话与上下文]
  Task --> Jobs[命令 / 外部请求 / 等待问题]
  Task --> Results[交付物与证据]
  Task --> Resume[暂停 / 取消 / 重试 / 恢复]
  Session --> Tools[工具执行]
  Tools --> Backend[Native / Linux / Remote]
  • 聊天是任务的交流界面，不必把所有业务状态编码成一段用户消息/助手回复。
  • 提醒是任务触发器；“提醒已投递”与“任务已完成”要分开显示。
  • 目标是一项跨多轮的持续任务，不应仅靠模型不停自我续跑；系统要知道预算、进度证据和阻塞原因。
  • job 是任务的一部分，提供输出/状态/取消；不要让它只在当前进程里有意义。
  • 工坊是任务的交互前端和交付物之一，页面的数据、Agent 请求与能力范围应各自明确。
  • GUI 是设备操作能力，适合没有结构化 API 的剩余步骤；有系统/服务 API 时优先用结构化接口提高稳定性。这是本项目能力边界的推断建议，不是本轮外部任务成功率实验。

先统一概念和状态，不要求立即把 UI 改成复杂任务看板。当前聊天中增加可信的等待/恢复/交付状态，也能得到实际收益。

不需要一开始变成十几个 Gradle 子项目。先在现有 runtime 内按下表建立包/接口和所有权，等边界稳定再分构建模块。

边界 统一负责 调用方不得自己做

runtime 内的 Android Keystore/DataStore/SQLite/Log 实现可逐步移到 app infrastructure 或 android adapter；纯领域接口不必 import Android。短期不急于多平台，但这样能独立测状态机，也给未来 Linux/remote 后端留下真实接缝。

4. 在动手前固定的数据模型与不变量

最小公共模型

模型 必须字段/语义
Task taskId、sessionId、来源、状态、created/updated、revision、恢复策略、预算
Run runId、taskId、epoch、source、state、started/settledAt、outcome、usage
PendingCommand commandId、sessionId、epoch、source、幂等键、排队/接受/完成状态
ToolExecution callId、runId、工具/作用域版本、输入摘要、状态、输出引用、取消/未知结果
OutputRef 任务私有文件或可回读存储、字节游标、截断/清理策略
Question requestId、taskId/sessionId/callId、题目、状态、答案、deadline/恢复策略
Artifact 稳定 id、类型、路径/URI、工作区、生成者、存在性/可打开状态
CapabilityScope 允许工具、文件根、创意数据范围、Native 能力、网络/运行器、预算

不应把消息 JSONL 和上述所有状态强塞成一个大文件，也不应复制两套消息权威。SDK JSONL 保持模型上下文/消息权威；应用任务记录有自己的事务，使用明确外键/修订号连接。

验收前必须成立的十条规则

  1. 同一 session 同一时刻只有一个可修改模型执行状态的拥有者；所有入口走该所有者。
  2. 每个 run 只有一个最终 outcome；开始、请求停止、完全停止有不同状态。
  3. Stop 会取消尚未开始的自动重试/续跑，旧 epoch 的任务不能复活。
  4. 进程重启后能区分已完成、可重试、等待用户和结果未知；不会假装所有任务继续运行。
  5. 已投递提醒有幂等键和确认点；重复唤醒不重复执行，崩溃窗口不静默丢失。
  6. 工坊默认能力是显式允许列表；本创意的数据边界不能靠名字过滤或提示词保证。
  7. 所有命令输出可限量保留并按游标读取，任何上游缓冲都不能无限增长。
  8. 凭据最新意图按序提交；旧刷新不能在登出/换 Key 后覆盖新状态。
  9. 升级失败保留旧可用安装与账号数据，记录/技能/实际二进制保持一致。
  10. UI 从权威快照和事件投影；缓存、事件丢包或页面重建不改变任务执行事实。

5. 工具与执行环境如何进一步整合

原生、Linux、远程用同一执行契约

现有 ShellExecutor 接缝应继续保留，但扩展为“开始/输出/等待/取消/关闭”的运行器契约。PRoot、Termux 或远程执行器的能力必须可查询：是否持久任务、是否可隔离、是否可访问共享目录、可用资源、最大输出。不要让界面通过某个类是不是 LinuxEnvironment 推断能力。

前台 bash 超时与后台 job 不必自动互相转换；用户/Agent 可以显式选择。无论选择哪条路，都应得到可解释的终态和输出引用。PRoot 的输出存到 App 管理的任务目录，再把有限尾部喂给模型，后续需要再按游标读取。

文件修改需要按 canonical workspace/path 协调，不仅按单个 session 的 FileMutationQueue。高价值更新可采用读时观察版本、提交前检查、临时文件原子发布；bash 直接写文件无法完全纳入原生 edit 队列，应在契约中承认并检测外部变化。

能力范围不等于每次审批

产品当前明确“不做通用审批系统”，这不是本报告要求推翻的点。可以在不增加每次弹窗的前提下，为主助手、工坊一次性 Agent、远程 Agent 设定不同默认能力作用域。用户明确启用插件/共享目录后，在该范围内直接执行；工坊不应自动继承整个主助手环境。

7. 一次完整整合的执行顺序

这是一项完整的系统整理，每一阶段服务同一组不变量；不是每次选一个简单任务做演示再追加补丁。

阶段 先固定的产物 实施范围 退出条件
A：契约冻结 数据模型、状态迁移表、来源/取消/恢复/能力/路径/输出契约、验收矩阵 文档和接口设计，尚不迁移执行语言 所有现有入口都能映射到契约，没有第二套权威
B：运行核心 SessionCoordinator、epoch、settled、重试预算 Host/SDK adapter，UI 只提交命令 多入口/停止/重配/取消场景通过
C：数据可靠性 JSONL 尾部修复、凭据顺序、任务/问题/outbox pi2kotlin + 应用持久层，分别发布/集成 崩溃注入后无丢新记录、无旧任务复活
D：能力与环境 Scoped 工具、Runner/output/file contracts、插件事务 工坊、shell、插件；日历日期专项修复 范围越界被拒、升级回滚、无界输出消除
E：界面与性能 feature coordinator、索引、增量解析、资源预算 大组件/缓存/存储读取关键路径 交互不退化，性能数据可重复；真机测试另按授权执行

不先改 UI 样式、不先换 Agent 引擎；优先改最难靠界面补救的执行秩序。每个阶段有可 review 的变更边界与回滚路径，避免一次重写 4.5 万行。
