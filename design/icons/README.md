# Icon sources

The single hand-maintained entry point for general UI icons in the app. One icon = one source file in a category directory + one entry in `catalog.json`; runtime resources, `DdIcons.kt` and the category preview are all generated by `gen.mjs`, and generated output is never edited by hand.

## Structure

```
design/icons/
  catalog.json          the single registry: category, Chinese name, DdIcons member, upstream path
  gen.mjs               generator (node, no dependencies; --check detects drift)
  preview.html          category preview page (generated; icons read the source files in this directory)
  navigation/ action/ status/ file/ chat/ ai/ system/
                        <id>.png | <id>.xml
```

## Naming

- Source files are `<id>.png|.xml`, with a snake_case id taken from the semantic name within the category (such as `menu`, `folder_open`, `audio_high`).
- Generated resources are `ic_<category>_<id>.png|xml` under `design/src/main/res/drawable-nodpi/` and are tinted uniformly by `DdIcon`.
- `DdIcons` member names keep their historical spelling (`DdIcons.Add` and so on) and are mapped by the `dd` array in `catalog.json`, so call sites need no changes.

## Categories

| Directory | Category | Contents |
|---|---|---|
| `navigation` | Navigation and direction | Menus, back, expand and direction indicators |
| `action` | Actions | Add, share, download and edit actions |
| `status` | Status and feedback | Confirmations, hints and notifications |
| `file` | Files and data | Files, folders, attachments and data types |
| `chat` | Conversation and voice | Conversations, voice and messages |
| `ai` | Intelligence and integration | Agents, models and extension capabilities |
| `system` | System and device | Settings, appearance, devices and tools |

## Generation

From the repository root (`app/`):

```
node design/icons/gen.mjs
node design/icons/gen.mjs --check
```

Output: `design/src/main/res/drawable-nodpi/ic_<category>_<id>.png|xml`, `design/src/main/kotlin/io/github/whywood/deepdeep/design/DdIcons.kt` and `design/icons/preview.html`. The script removes the old naming (`ic_milo_*`, `ic_dd_*`) and generated resources that are no longer registered.

`--check` only compares and writes nothing; it exits non-zero on drift, so CI can use it directly.

## Adding or replacing icons

1. Put the source file in the matching category directory, with the file name as the id; use a 256×256 RGBA PNG for bitmaps, and a 24 viewport, 2.1dp round-cap stroke in pure black for hand-drawn vectors.
2. Register `id`, `category`, `name_zh`, `dd` (array of DdIcons member names) and `upstream` (path relative to the Milo package, or `null` for hand-drawn vectors) in `catalog.json` under `icons`.
3. Run generation and build. Source files without an entry, and entries without a resource, both fail the script.

## Visual specifications

- Bitmaps come from `assets/milo-modern-icons-200-revised/regular/`: 256 canvas, stroke width about 1.75dp, `#273140` lines, glyphs covering about 85% of the canvas, and only icons the app actually uses.
- The few line icons with no Milo equivalent are hand-drawn vectors: 24 viewport, 2.1dp round-cap stroke, pure black so they can be tinted.
- Both are tinted uniformly by `DdIcon`; never call `painterResource` directly in product code.

## Brand and platform assets

Provider logos (`assets/pi-provider-logos/`), vendor logos (`assets/vendor-logos/`) and launcher icons (`assets/branding/`) each carry their own manifest, source licensing and generation flow, and are reused across directories by the market and notifications, so they stay out of the general icon directory; see `assets/README.md` and the preview page footer for the index.
