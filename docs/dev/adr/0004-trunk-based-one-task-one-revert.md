# 0004 trunk-based + 一个任务一个 squash 提交 + 一次 revert

- 状态：已采纳 · 2026-10-30 · 任务 M1-8（相关 M1-3）

## 背景

协作规则的现状（均已入库）：

- 一个任务 = 一张卡 = 一份简报 = 一个分支 = **一个 squash 提交 = 一次 revert**（`docs/dev/refactor/PLAYBOOK.md §1`）。
- 提交标题 `type: 祈使句摘要 [ID]`，squash 合并，进主干只能一条；body 三行必填 `验收:`、`回滚:`、`不在范围:`（`PLAYBOOK.md §9 提交规范`、`CONTRIBUTING.md §步骤`、`AGENTS.md §4 必须`）。
- 回滚演练每任务必做：`git revert --no-commit <sha>` 后 `./scripts/verify.sh` 必须干净通过（`PLAYBOOK.md §11 回滚演练`）。
- PR 预算：`git diff --stat` ≤400 行 / ≤15 文件 / ≤2 模块，超了先拆成可顺序合并的小 PR（`PLAYBOOK.md §3 DoD` 第 6 条、§5 大 diff）。
- 计划视图已定“不引 Git Flow”（`docs/dev/refactor/README.md §5 已定决策`），回滚分 L0–L3 四级（同文件 §6 回滚）。

M0/M1 的提交按任务 ID 组织（例如 `1cebafe [M1-1]`、`cffc5f3 [M1-2]`、`5d0eeec [M1-3]`、`07ee457 [M1-7]`）；主干为 `master`，重构期在 `refactor/team-foundation` 上线性推进，没有长期 feature/develop 分支。个别同一交付物的两张卡合并为一条提交（`b5ba861 [M1-4/M1-6]`），回滚时仍按卡说明影响。

为什么必须现在决定：① 重构期每个任务都可能改变行为，失败代价是“丢数据 / 全 App 回归”（`PLAYBOOK.md §7 human-only`）；② 一旦提交混入多个任务，故障时无法只撤坏的一半，**回滚能力在事后无法补救**；③ 没有这道纪律，PR 模板的 G1/G2/G3 与 findings 对账（提交标题带 ID）都会失效。

## 决定

**任务以从主干切出的短分支开发，进主干 squash 成一个提交；一个任务 = 一个提交 = 一次 `git revert`；提交预算 ≤400 净增删行 / ≤15 文件 / ≤2 模块。**

落地口径：

1. 分支：`task/<id>-<slug>`（`CONTRIBUTING.md §工作方式`）；不在主干上直接改，不保留跨任务的长期分支。
2. 提交：标题带任务 ID；body 固定三行；squash 后一个任务只留一条提交（`PLAYBOOK.md §9 提交规范`）。
   唯一例外是**记账提交**：任务完成后单独提交一行 `docs: mark <ID> complete`（回填 `tasks.tsv` 状态、必要时同步进度表）。它不含实现，不得夹带代码；回滚时与实现提交一并 `git revert`，不允许只回滚记账提交而留下已删/已改的实现。
3. 回滚：每个任务交付时贴回滚命令；`git revert <sha>` 必须一行完成；需求涉及数据变更时在 PR 写清“数据影响”（`AGENTS.md §4`）。
4. 预算：超 400 行 / 15 文件 / 2 模块时，先在任务卡说明理由或拆卡；拆不开退回重做，不允许“一次 36k 行”（`PLAYBOOK.md §3 DoD` 第 6 条、§5）。
5. 一个提交内不做“顺手优化”、不重排/格式化无关文件（`AGENTS.md §5`）；跨 >2 模块且无 ADR 的改动直接退回（`CONTRIBUTING.md §两条额外硬规则`）。

## 为什么“回滚粒度”比“diff 可读”重要

- diff 可读可以通过 PR 模板、G2 证伪、评审把关获得；**回滚粒度是事后唯一还能止损的手段**。代码/数据已经坏掉时，评审帮不上忙，一行 `git revert` 能。
- 混合提交 = 回滚要手工挑拣，等于失去回滚能力；squash 把“一个任务一个可撤销单元”固化下来，**diff 可读只是副产品**。
- G2 降低出错概率，回滚限制出错后果，两者分工不替代：复核证明 G2 有效（128 条评审第二遍仍揪出 15 条有害建议，`PLAYBOOK.md §2` G2 硬规则），但它仍是概率性保障。
- 回滚能力直接对应数据安全：squash 提交 + 回滚演练 + 上一版 APK 回退（`docs/dev/refactor/README.md §6 回滚`）组成数据事故的止损链；ADR-0001 的签名问题说明“数据丢了就不能靠回溯代码找回”。

## 被否决的方案

- **Git Flow（develop/release/hotfix 长分支）**：分支多、合并点分散，回滚单位从“任务”退化成“合并批次”，且单人 + agent 的项目没有发布列车需求；`docs/dev/refactor/README.md §5 已定决策` 已列为不做。
- **每个任务保留多条细提交进主干（merge commit 或 rebase）**：能定位到行，但回滚要 revert 整条链或手工挑拣，且主干历史无法用“带 ID 的单提交”机器对账（`PLAYBOOK.md §9 提交规范`）。
- **一个 PR 混多个任务（“顺便一起”）**：验证不可分、回滚不可分；故障时无法判断是哪个任务引入的。
- **只靠 PR 评审、不要求一行回滚**：在单人为主、CI 只覆盖机器闸门的环境里，评审是概率性保障，不能替代可撤销性。
- **CODEOWNERS / 强制审批流**（`PLAYBOOK.md §6` 第 15 条）：单人期成本真实、收益未证；等出现第二个人再评估（master 分支保护已随 M1-7 落地）。

## 后果

- 代价：每个任务开工前必须先想清“怎么独立验证、怎么独立回滚”，拆任务成本前置；并行 agent 必须遵守 scope 不相交（`PLAYBOOK.md §5`），否则单提交的边界会被别的工作污染。
- 主干历史是“任务流水账”而不是“精细开发史”：单条 squash 提交内的试错过程不留痕，需要时看 PR 正文与 G2 记录。
- **被永久驳回的评审建议**：以“diff 更细、便于 review”为由让多个任务共用一条提交或保留多提交主干；引入 Git Flow/长分支；跳过回滚演练的“节省时间”做法。
- 不可交给 agent 单独完成的改动仍标 human-only（`PLAYBOOK.md §7 human-only`）；回滚粒度再好也不改变“先停手”的规则。

## 推翻条件

- **出现多名常驻维护者并需要正式 code review 审批流** → 可引入 CODEOWNERS/更严的分支保护，但“一个任务一个 squash 提交 + 一行 revert”保留。
- **发布形态需要 hotfix/cherry-pick 分支**（例如商店版本回滚）→ 可加 release 分支，主干仍单任务单提交；hotfix 的提交必须同样带 ID 与回滚说明。
- **连续多次任务无法压进预算**（例如连续 3 个任务超 400 行/15 文件）→ 先重估预算数字与拆分方式；预算可调，**回滚粒度不可退让**。
